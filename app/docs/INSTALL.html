What is in the package

One file: ner-analyzer-4.4.0-windows.zip, about 100 MB, accompanied by ner-analyzer-4.4.0-windows.zip.sha256 to check the copy.

Inside the zipWhat it is
setup.batThe installer, and the only file to run: installs into a folder of its own, replaces a previous version keeping its data, registers the tasks, starts the server, opens the browser and then deletes the unzipped package and the zip. Section Installing.
setup-noadmin.batThe same installer without the Windows administrator prompt (setup.bat --no-admin): for a managed computer where the rights cannot be granted. It installs for the account signed in, in that account's profile, and nothing else differs.
install.bat · start.bat · stop.batThe pieces setup.bat runs underneath. Opening install.bat in the unzipped package hands over to setup.bat, so it does the same thing.
autostart.batStart at sign-in and install the watchdog; autostart.bat remove undoes it.
backup.bat · run-tests.bat · build_package.batBackup and restore; the test suite; building a new package from this installation.
reset-password.batA new password for an account that forgot it, on this computer (Mac: mac/reset-password.command). See Common problems.
backend\ · frontend\ · tests\ · tools\The application: server, compiled screens (backend\app\static), tests and operating scripts.
vendor\python\Python 3.12 itself (64-bit): the official python.org embeddable package, 11 MB, signed by the Python Software Foundation. The installer unpacks it into .python\. It is what makes installing Python unnecessary.
vendor\wheels\Every Python package the application depends on, already downloaded, built for that Python 3.12 on 64-bit Windows — and pip itself, which the installer uses to install them. It is what makes the internet unnecessary.
docs\This manual, the one-page Quick install (QUICK-INSTALL.html) and the User manual (HTML and PDF), the project history and the technical notes.
VERSION · CHANGELOG.md · PACKAGE.txt · MANIFEST.txtThe version, what changed in each version, the package's record (version, date, counts) and the file list with each file's hash.
LICENSE.txt · NOTICE.txt · THIRD-PARTY-NOTICES.txtThe licence (GNU AGPL-3.0, full text); the author credit Created by Marcelo Barbosa, kept as an additional term of the licence (section 7(b)); and the licence of every third-party component the package carries.
data\Empty, holding only a .keep marker. It is where the database and the uploaded documents will be born. setup.bat does not copy it into the target folder.
The package carries no data

No projects, no drawings, no TEAP, no accounts and no password hashes. That is a security property, not tidiness: the builder refuses a package that includes the data folder, and checks the file list before writing the zip. The practical consequence: the USB stick with the package is just software, and can travel like any installer and be shared freely under the licence (Version and licence).

What the computer needs

ItemWhy
Windows 10 / 11, 64-bitThe compiled packages in the zip are for 64-bit Windows. (A Mac with Apple Silicon has its own package: section Installing on a Mac.)
Visual C++ runtimeThe numeric packages use Microsoft's msvcp140.dll, which virtually every Windows already has (any Microsoft Visual C++ Redistributable 2015–2022 installs it, and almost every program brings one). When it is missing, the installer places the copy bundled inside the packages next to Python, with no administrator — and says on screen which of the two happened. There is nothing to install beforehand.
~1 GB of diskAbout 350 MB of that is the private Python (.python\) the installer builds inside the folder; the rest is the package and room for the first books.
Administrator rightsNot required. Nothing in the installation needs them: the application goes into the person's own profile, its two scheduled tasks are per-user, the server listens on 127.0.0.1 only. setup.bat asks Windows for them when it starts, because on some managed computers a script run without them is refused by policy before it starts; when they are refused — or cannot be granted at all — it offers to install for this account only, which is exactly what it does with them. setup-noadmin.bat (or setup.bat --no-admin) skips the question. If they are granted, they must belong to the person who will use the application, signed in as themselves: typing another account's administrator name and password into the prompt would install the application in that other account's profile, and setup refuses it (section Common problems).
A browserGoogle Chrome, Microsoft Edge or Mozilla Firefox, in a current version. Safari and Internet Explorer are not supported.
Memory8 GB works; 16 GB leaves room to export a 75-page book with the browser and Outlook open.

That is the list. No Python installed, no internet, no database server, no web server, no Node.js, no Docker — and no artificial intelligence of any kind: nothing in the folder calls out to any model, service or account.

Python comes in the package

There is nothing to install before the application. The Python it uses lives inside its own folder.

The application is a server written in Python. Rather than require every computer to have Python installed — a download, an installer, a PATH option to tick — the package carries in vendor\python\ the official python.org embeddable package: the complete Python 3.12 for 64-bit Windows, in an 11 MB zip made precisely to be shipped inside a program. install.bat unpacks it into .python\, beside backend\, and installs the packages from vendor\wheels into it.

ConsequenceIn practice
Nothing outside the folderThat Python is not added to PATH, does not appear in Programs and Features, does not touch the registry. Deleting the folder deletes the Python with it.
Isolated from the rest of the machineThe file .python\python312._pth is that Python's entire search path: the standard library, the packages installed in .python\Lib\site-packages and the application's backend\. Another Python installed on the machine, environment variables such as PYTHONPATH and user packages are ignored. Two Pythons on the same machine never see each other.
If a Python is already thereA Python installed on the machine is not used, not changed and not required: with vendor\python\ in the package, the installer always uses the embedded Python. A .python\ already in the folder (a previous installation) is deleted and unpacked again from the package's zip; if the server has it in use, the installer stops with The previous runtime is in use — stop.bat and run it again. (setup.bat never meets this: in update mode it stops the server and moves the whole old installation aside before installing.)
Provenance checkedThe package builder only accepts the python.org zip whose SHA-256 is pinned in tools\make_package.py, and the installer checks the digital signature of python.exe (Python Software Foundation) after unpacking, printing the publisher on screen.
Fixed version: 3.12.10The packages in vendor\wheels are built for Python 3.12, and 3.12.10 (April 2025) is the last 3.12 published with Windows binaries — later ones are source-only security releases. Changing the Python means changing the whole package set, and is a new version of the application, not a file swap.
For the developer

A copy of the code without vendor\python\ (a development checkout) makes install.bat use the Python installed on the machine (3.11 or newer, 64-bit, preferably 3.12) and build a virtual environment in .venv\. Every script looks for .python\ first and .venv\ second, so the two arrangements coexist and the package built on a development machine always carries the embedded Python.

Installing: setup.bat

Unzip the file anywhere, right-click setup.bat and choose Run as administrator — or, on a computer where you cannot get administrator rights, double-click setup-noadmin.bat. When it finishes, the application is installed in a folder of its own and running, the browser is open on it, and the installation files (the unzipped folder and the zip itself) are gone. Only the application is left.

  1. Unblock the zip (optional, but it saves a Windows prompt per script): right-click ner-analyzer-4.4.0-windows.zip → Properties → tick Unblock at the bottom → OK. Without it, Windows may show Open File – Security Warning before the script runs; click Run.
  2. Unzip the file: right-click → Extract All…. Where does not matter: the Downloads folder is fine, because nothing will stay there. Do not run anything from inside the zip without extracting it. You get a ner-analyzer folder with setup.bat inside.
  3. Right-click setup.bat → Run as administrator, and answer Yes to the Windows prompt. A plain double-click works too: setup notices it has no administrator rights, asks Windows for them, and carries on in a new window. Without administrator rights — a managed computer where they cannot be granted — double-click setup-noadmin.bat instead: the same installation, for your account only, with no prompt. The window shows the source folder, the target folder and the mode (install or update), then runs by itself through six numbered steps. Two to five minutes, no internet.
  4. The browser opens at http://127.0.0.1:8000 as soon as the server answers, and an NER Analyzer shortcut appears on the desktop. On a new installation, create the first account (section First sign-in).
  5. The last screen reads Installed - version 4.4.0 and the folder the application went to; on an update, also the version it replaced and where the old one was kept. Press a key: the window closes and, about three seconds later, the unzipped package and the zip are deleted.

If a step fails after the old version was moved aside

The copy, install.bat or the runtime check failing in update mode puts everything back: the data\ folder returns to the old installation, the half-built new folder is removed, ner-analyzer.previous is moved back to ner-analyzer, the tasks are re-enabled and the old server is started (Version 2.x.y is back in …, with its data.). The data is never deleted at any point: it moves with the installation, and its backup is inside it. If even the move back fails, setup says where each part is and deletes nothing.

What it refuses

Running from a copy that is not a built package (no MANIFEST.txt, or no Python under vendor\python). Installing into the unzipped folder itself, inside it, or into a folder that contains it (the unzipped folder is deleted at the end). Running as another account than the person signed in. When a step stops with an [X] message, the package is not deleted: the message says why, the tasks held in update mode are re-enabled, and the package can be run again once the cause is fixed (Common problems). The [*] warnings of steps [4/6] and [5/6] do not stop the installation.

Why the clean-up

Deleting the zip and the unzipped folder keeps the machine tidy: one installed copy, and no stale installer left behind to be run again by mistake. It is not there to stop copies: anyone may copy and share the package under the licence (LICENSE.txt, NOTICE.txt and section Version and licence). To keep the package, run setup.bat --keep-installer.

After setup.bat there is no vendor\ in the installed folder

Deleted on purpose: it is installation weight, not application weight. The consequence: the installed folder's install.bat cannot rebuild .python\ on its own; do not run it there. To repair or update an installation, run the setup.bat of a package (the same version or a newer one). A record of what setup.bat did is in data\setup.log.

install.bat and start.bat

In the installation package, install.bat is not a second way in: opening it hands over to setup.bat (This is the installation package: handing over to setup.bat…), so whoever opens it by habit gets the same installation, in the same folder, with the same clean-up.

install.bat installs in place only where there is no setup.bat beside it, or no MANIFEST.txt: in a development checkout, where it builds a .venv\ with the Python installed on the machine (section Python comes in the package, For the developer), and when setup.bat itself calls it in the target folder. It writes nothing outside its folder, and it can be run again at any time with the server stopped: it rebuilds the private Python from scratch and never touches data\.

start.bat is not needed after setup.bat: the server is already running with no window, and starts by itself at every sign-in. It stays in the installed folder for whoever wants the server in a console window (closing the window stops it), for example to watch it start after a problem.

Installing on a Mac

The same application, packaged for Apple Silicon (M1 or later) on macOS 11 or later: ner-analyzer-4.4.0-macos-arm64.zip, about 110 MB, with ner-analyzer-4.4.0-macos-arm64.zip.sha256 to check the copy (shasum -a 256 in Terminal). No administrator password, no internet, nothing to install first.

In the packageWhat it is
setup.commandThe installer — the macOS twin of setup.bat.
vendor/python/A standalone CPython 3.12.15 for Apple Silicon (python-build-standalone, release 20261009), pinned by its SHA-256 when the package is built.
vendor/wheels/The same 48 Python packages, at the same versions, as the Windows package, built for macOS on Apple Silicon (requirements-lock-mac.txt).
mac/start.command, stop.command, backup.command, run-tests.command, autostart.command, uninstall.command — they stay in the installed folder.

Steps

  1. Double-click the zip in Downloads (Archive Utility unzips it).
  2. Open Terminal, type bash and a space, drag setup.command from the unzipped ner-analyzer folder into the window, press Return. To choose another folder, add it after the script: bash …/setup.command ~/Documents/ner-analyzer.
  3. The browser opens at http://127.0.0.1:8000; create the first account (First sign-in).

Double-clicking setup.command in Finder works too, but a file downloaded from the internet that Apple has not notarised is held back the first time: macOS says it could not verify the developer. Click Done, open System Settings → Privacy & Security, scroll to the message about setup.command and click Open Anyway. Running it through bash in Terminal, as above, does not ask.

What setup.command does

StepWhat happens
[1/6]Checks the Mac (Apple Silicon, macOS 11 or later) and the package, and takes the downloaded-from-the-internet mark off the unzipped files (they are your own files: no password). Default folder ~/Applications/ner-analyzer. An existing installation there means update.
[2/6]On an update: backs up the database into the installation's data/backup-…, stops its server, moves it aside to ner-analyzer.previous and carries its data folder into the new one. If anything later fails, the previous version is put back, data first.
[3/6]Copies the application (never a data folder, never the installer itself).
[4/6]Unpacks Python into .python/ and installs the bundled packages into it, offline (pip --no-index --no-deps, the user's own Python packages ignored), then checks every component loads.
[5/6]Registers a launch agent for your account (~/Library/LaunchAgents/com.marcelobarbosa.ner-analyzer.plist): the server starts now, at every sign-in, and again if it stops on its own — on a Mac launchd does what the watchdog task does on Windows. Waits for /healthz, opens the browser, writes NER Analyzer.webloc on the Desktop. With --no-services nothing is started.
[6/6]Removes vendor/ from the installation and ner-analyzer.previous, then the unzipped package and ner-analyzer-4.4.0-macos-arm64.zip with its .sha256 (beside it, one level up, or in Downloads). --keep-installer keeps them. The log is data/setup.log.

Afterwards

Stop the server with mac/stop.command (it starts again at the next sign-in), start it with mac/start.command, back up with mac/backup.command (the same tool as backup.bat), run the tests with mac/run-tests.command. mac/uninstall.command stops it, removes the launch agent and the Desktop link, and deletes the application — the data folder only if you type delete. The data, the backups and the restore work exactly as on Windows: see Where the data lives and Backup and restore. A backup made on Windows restores on a Mac and the other way round.

Not tested on a Mac by the builder

The macOS package was built and its installer rehearsed end to end on Linux (same shell steps, a Linux runtime in place of the Mac one: install, update with backup, a broken package rolled back, tests passing in the installed copy, the server answering). The first install on a real Mac is the remaining check: if a step stops, the window says which and data/setup.log has the detail. A company-managed Mac may forbid scripts from Downloads or launch agents; IT has to allow them.

First sign-in

  1. At the end of setup.bat the browser is already open at http://127.0.0.1:8000. Later, open it with the NER Analyzer shortcut on the desktop, or type that address into Chrome, Edge or Firefox. Right after a reboot, give the server 20 to 40 seconds to start.
  2. The first screen is Create the first account: username, display name, password (at least 10 characters; a phrase you remember beats a scramble of symbols) and the password again. That account is an administrator and creates the others. There is no default user and no default password.
  3. You land on the Projects tab. The PT-BR / EN button in the top bar switches the interface language. From here on, the User manual.
Another port

If port 8000 is already taken by another program, start.bat --port 8080 starts on another one. For the sign-in task and the watchdog, set the environment variable NER_PORT to the same port before running autostart.bat. The desktop shortcut always points at port 8000.

Starting by itself, and the watchdog

Optional, but this is how the application behaves on a working machine: no window, up after any reboot, and back within two minutes should it ever stop answering.

  1. Double-click autostart.bat. It creates two Windows scheduled tasks for the person signed in (setup.bat runs it for you): NER Spatial Coverage Analyzer (at that person's sign-in, starts the server with no window; log in data\server.log) and NER Analyzer watchdog (every two minutes, checks that the server answers and starts it again if not; log in data\watchdog.log). Neither needs administrator rights.
  2. To start it now without signing out: schtasks /run /tn "NER Spatial Coverage Analyzer" in a Command Prompt — or simply wait for the watchdog, which starts it within two minutes.
  3. To stop the server: stop.bat. To undo both tasks: autostart.bat remove.

The task fires at sign-in, not at boot: the application reads and writes a folder in your profile, so it runs as you and needs no stored password. It fires at your sign-in only — it is registered for the account that ran autostart.bat (tools\signin-task.ps1), which is what lets an account without administrator rights create it; a task for every user of the computer is an administrator's to create. The watchdog goes through a .vbs precisely so that no black window ever flashes on screen every two minutes.

Should Windows refuse the sign-in task all the same, autostart.bat says so ([*] Windows refused the sign-in task) and installs the watchdog regardless. The application then still comes up by itself: the watchdog starts the server within two minutes of signing in, and keeps it up.

Checking it works

With the server running, open http://127.0.0.1:8000 and confirm:

  • the sign-in screen appears, with the Where this data lives statement and version 4.4.0 under the title;
  • you create the administrator account and reach the Projects tab;
  • the left-hand navigation lists the steps from Import to Reports, and the sidebar reads version 4.4.0;
  • http://127.0.0.1:8000/healthz answers {"status":"ok","version":"4.4.0"}.

For a deeper check, double-click run-tests.bat: around 900 tests, one to two minutes. All passing (All tests passed), the installation is sound — every component loads, the rules compute what the manual says, the exports have the shape the manual describes.

Backup and restore

CommandWhat it does
backup.batWrites data\backup-YYYYMMDD-HHMMSS\ with a consistent copy of the database (through SQLite's backup API — valid even while the server is running), the uploads folder and, when the installation has one, criticality-matrix.xlsx. A BACKUP.txt inside says the version, the time, the size and whether the matrix is in it.
backup.bat --to D:\NER-backupsThe same, into a folder or drive of your choice — which is what makes the backup survive the disk.
backup.bat --restore data\backup-…Puts a backup back. With the server stopped (stop.bat) — the script refuses while it is answering. The database and uploads that were there are moved to data\replaced-…\, not deleted; delete that folder once you are sure. The installation's own criticality matrix is replaced only when the backup carries one. The next time the server starts, it points the record of every uploaded file at this installation's data\uploads, whichever folder the backup was taken in.

When: before deleting a project, before installing a new version, and periodically to an external drive. Backups under data\ accumulate; delete old ones from time to time.

Carrying projects from another machine

The recommended way is to export from the other side (the Reports tab: the workbook, the CSV and the marked-up PDF) and re-import the VDB and the TEAP on the new machine. The new installation is clean, its history belongs to it, and the decisions are retaken with the drawing in front of you.

Copying everything is possible, and it is what you do to change computers without losing anything:

  1. On the source machine, backup.bat --to E:\ (a USB stick or a network folder). The backup holds the database, the uploads and the criticality matrix when there is one.
  2. On the new machine, install the application (sections above) and do not create the first account yet — or do; it will be replaced by the accounts in the backup.
  3. With the server stopped, backup.bat --restore E:\backup-…. Start it. The database migration, if the new version needs one, runs by itself on first start — and on that start the server points the record of every drawing and TEAP at this installation's own data\uploads, so the folder, the drive and the Windows account need not be the ones of the source machine. Each record is moved only when the file is here and is the same file (same SHA-256); each move is written to the project's audit log.
Two things before copying the database

First: the copy carries the accounts with their password hashes, along with every project, drawing and the audit log. The USB stick becomes the database — treat it as one, and wipe it afterwards.

Second: from then on there are two databases that do not talk. Work done on one is invisible to the other and there is no merge. Decide which machine is authoritative before anyone starts working, not after.

Updating to a new version

A new version arrives as another zip, with another number (ner-analyzer-4.4.0-windows.zip). The CHANGELOG.md inside says what changed. Install it exactly like the first time: unzip, right-click setup.bat → Run as administrator, or double-click setup-noadmin.bat (with the same target folder, if you chose one).

  1. Setup recognises the installation and says Replacing version 3.x.y - its data is kept. No administrator rights are needed: setup-noadmin.bat updates an installation made with or without them, for the account signed in, and keeps every project, account and drawing.
  2. It holds both tasks, backs up the database into data\backup-…\, stops the server, moves the old installation aside to ner-analyzer.previous and moves its data\ into the new folder.
  3. It installs the new version in the now-empty folder, registers the tasks again, starts the server, opens the browser and deletes the package. The database migration, if the new version needs one, runs by itself on first start.
  4. In the browser, Ctrl+Shift+R once: the sidebar shows the new number and the amber the application was updated… pill goes.
  5. Once the new version works, delete %LOCALAPPDATA%\Programs\ner-analyzer.previous. The next update removes it anyway before keeping the one it replaces.

To go back to the previous version by hand: stop.bat, rename ner-analyzer to anything else, rename ner-analyzer.previous to ner-analyzer, and move the data\ folder from the first into the second. If the database was already migrated by the new version, restore the backup setup took (backup.bat --restore data\backup-…) instead of using the migrated one.

Uninstalling

  1. If you want to keep the data: backup.bat --to a folder outside the application.
  2. In the installed folder, autostart.bat remove (removes both scheduled tasks) and stop.bat.
  3. Delete the ner-analyzer folder (%LOCALAPPDATA%\Programs\ner-analyzer on an installation made by setup.bat), the ner-analyzer.previous folder beside it if there is one, and the NER Analyzer desktop shortcut. There is nothing else: no registry entry, no service, no file outside those folders. The application's Python lived inside it and goes with it.

Building the package

For whoever maintains the application: how to produce a version's zip from the development installation.

  1. The version is in VERSION, in frontend\package.json and at the top of CHANGELOG.md — all three equal. run-tests.bat refuses a mismatch.
  2. The compiled screens must carry that version: cd frontend && npm run build (only the development machine needs Node.js).
  3. Double-click build_package.bat. It needs the internet once: it downloads into vendor\wheels the Python packages of requirements-lock-win.txt for Python 3.12 / 64-bit Windows (~100 MB, pip included) and calls tools\make_package.py, which fetches the python.org embeddable package into vendor\python (11 MB, once) and writes dist\ner-analyzer-<version>-windows.zip and the .sha256. build_package.bat --keep reuses the packages already downloaded.

The builder refuses to build when: the data folder or any database, log or upload would enter the package; a file carries a personal Windows path (C:\Users\…); the compiled screens or the manuals do not carry the version in VERSION; the Python zip does not match the SHA-256 pinned in tools\make_package.py; the pip or numpy wheel is missing from vendor\wheels; or a required file is missing. The unpacked .python\ folder never enters the package — only the zip it is born from. The single-machine diagnostic scripts under tools\ stay out by list; only the operating ones travel. setup.bat and setup-noadmin.bat are required in the package.

The macOS package is built by the same packager, on any system: python tools/make_package.py --platform mac → dist/ner-analyzer-<version>-macos-arm64.zip. It needs vendor/python-mac/cpython-3.12.15+20261009-aarch64-apple-darwin-install_only.tar.gz (fetched once from GitHub and refused unless it hashes to the pinned value) and vendor/wheels-mac/, filled with pip download --platform macosx_11_0_arm64 --platform macosx_11_0_universal2 --python-version 3.12 --implementation cp --only-binary=:all: --no-deps -r requirements-lock-mac.txt -d vendor/wheels-mac. It refuses a Windows wheel, a pin without exactly one macOS wheel, and a requirements-lock-mac.txt that drifts from the Windows lock. Every .command is written with its executable bit, so Archive Utility restores it.

Two editions

Both are built from the same source by tools\make_package.py. The team edition (the default) carries the private reference material of the folder backend\app\reference_private\: a client's list of space names and naming table, when the builder has them. The public edition — python tools/make_package.py --public, written as ner-analyzer-<version>-public-windows.zip or ner-analyzer-<version>-public-macos-arm64.zip — leaves that folder out (only its README.md travels) along with the archived manual under docs\history\, and refuses to build while any shipped text names an event, an organiser, a venue or an employer. The application works the same without the private material: the TEAP names alone filter the name-only room labels, and the Naming panel shows the application's own naming rule.
